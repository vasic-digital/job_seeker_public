## 2. Notes on the guards that EXIST

- **Hash chain of custody is strong and worth keeping:** one read, hashed, the same bytes sent (`templates.go:173-192`); approval pins the pair hash; any change returns the application to `draft_prepared` with the approval superseded (`service.go:331`, `TestRedraftAfterHashChange`). It protects *integrity*, not *suitability*: a perfectly intact wrong-date, link-broken PDF passes every one of these.
- **Fail-closed defaults:** unreadable caps count as 0 (`gate.go:101-115`), kill switch read error is "on" (`gate.go:38-51`), an absent overlay blocks live approval (`service.go:510-517`). New guards must follow the same polarity.
- **The umbrella gate is the only format guard,** and job_seeker trusts the manifest. There is no cross-check that a given PDF passed the *current* gate (F-03, G-10).

## 3. Cross-cutting design rules for new guards

1. **Three-valued:** pass / fail / cannot-determine; cannot-determine blocks live approval and is never recorded as a pass (umbrella convention `gates.py:13`).
2. **Test-first with a recorded RED:** each guard ships a fixture that fails on today's artifact (e.g. F-08 must fail the 260 current files) before the guard is written; then a mutation (re-introduce the defect) must turn the suite RED again.
3. **No personal data in fixtures or logs:** synthetic persona only; findings name file, check id and counts, never extracted text (same rule as `pdgate`).
4. **Deterministic substitution only:** FR-029 forbids generation. Personalization is a fixed template with typed slots (company, role, date, hiring contact) filled from operator-confirmed rows; no model writes prose.
5. **Guards run where the artifact changes hands:** at render (umbrella gate), at `Resolve` (manifest freshness), at `Approve`, and again at `HandoffComplete`.
6. **Every refusal is audited** with a reason code in the hash-chained audit table (FR-033).
